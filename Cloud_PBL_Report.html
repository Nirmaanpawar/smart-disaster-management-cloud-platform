1. Introduction

Catastrophic natural and man-made disasters, including urban flash floods, structural building collapses, severe seismic disruptions, and industrial fires, cause immediate loss of life and massive devastation to critical municipal infrastructure. During acute emergencies, terrestrial power grids, cellular communication towers, and surface transportation networks are frequently submerged or obstructed by debris, severing ground rescue access to vulnerable populations.

Cloud computing serves as the indispensable backbone for modern disaster engineering. By decoupling data ingestion and compute from localized physical machinery, cloud architectures provide on-demand scalability, multi-region fault tolerance, and universal web accessibility. Coupled with autonomous aerial drones, cloud-based emergency platforms enable first responders to survey wide hazard zones, pinpoint victims with satellite precision, and coordinate multi-branch rescue operations in sub-second timeframes.

1.1 Background

Conventional emergency response workflows rely heavily on retrospective reporting—principally panicked citizen phone calls (e.g., 911 or emergency dispatch hotlines). These voice-based calls suffer from severe location ambiguity, lack visual hazard context, and cannot reliably communicate environmental risks (such as rising floodwater currents, combustible gas presence, or structural instability). Unmanned Aerial Vehicles (UAVs) equipped with high-resolution optical cameras offer superior capabilities to penetrate severed zones. However, standalone drones without cloud connectivity suffer from localized data siloing, requiring physical SD-card retrieval or short-range RF links that fail to notify central rescue command centers in real time.

1.2 Motivation

A cloud-native, serverless approach is uniquely suited for disaster response for four critical reasons:

  • Elastic Scalability on Demand: Disaster events occur abruptly. A serverless cloud model scales compute and database resources instantaneously during mass-casualty surges without requiring upfront server capacity provisioning.
  • Pay-as-You-Go Cost: Utilizing AWS Free Tier serverless primitives (AWS Lambda, Amazon DynamoDB, Amazon S3, and Amazon API Gateway), municipal response teams can maintain continuous 24/7 readiness at ₹0.00 baseline operational expenditure.
  • High Availability & Multi-AZ Fault Tolerance: Hosting emergency state records across redundant AWS Availability Zones ensures continuous operations even if localized physical command posts experience localized blackouts.
  • Cross-Device Accessibility: Web-based tactical dashboards and WebRTC edge drone modules enable seamless coordination across field drones, mobile rescuers, and command headquarters through open web standards.

1.3 Scope of the Project

The scope of this project encompasses:

  • Designing an onboard UAV optical camera reconnaissance unit with tactical HUD, GPS locking, dual targeting modes (automatic AI and manual reticle positioning), and WebRTC video streaming.
  • Developing an event-driven serverless cloud ingestion API using AWS Lambda (Python 3.11) and Amazon API Gateway.
  • Persistently indexing emergency records in Amazon DynamoDB with sub-10ms query performance and multimedia evidence storage in Amazon S3.
  • Classifying operations into tactical disaster branches (Marine & Flood, Structural Collapse, Fire & Hazmat, Medical Triage) with dynamic Amphibious Boat and Road routing.
  • Building a responsive Rescue Command Operations Center with Esri defense GIS layers, real-time KPI metrics, and one-click dispatch lifecycle management.

4. System Design and Architecture

4.1 Proposed Architecture

The platform is structured into four decoupled, event-driven tiers:

  • Edge Reconnaissance Tier: Drone Camera module utilizing WebRTC optical media capture, tactical HUD overlay, GPS location tagging, and dual reticle modes (Automatic AI human detection at 96.8% and Manual touch-drag).
  • API & Ingestion Tier: Amazon API Gateway managing HTTPS REST endpoints, executing CORS pre-flight validation, rate limiting, and securely routing incoming JSON payloads.
  • Serverless Compute Tier: AWS Lambda (Python 3.11) validating schemas, calculating Haversine distance from Fleet Base, classifying disaster branches, uploading photo evidence, and updating database state.
  • Persistence & Operations Tier: Amazon DynamoDB NoSQL database for rapid telemetry queries, Amazon S3 for durable media storage, and AWS Amplify hosting the central Rescue Command Center.

4.2 Cloud Service Model and Deployment Model

Service Model: Function-as-a-Service (FaaS / Serverless) & Database-as-a-Service (DBaaS). Eliminates server provisioning, idle energy consumption, and patching overhead.
Deployment Model: Public Cloud (Amazon Web Services - AWS Asia Pacific Mumbai ap-south-1 & Sydney ap-southeast-2), providing multi-AZ fault tolerance and low edge latency.

5. Implementation

5.1 Methodology and Timeline

The project was executed across five sequential phases spanning a 10-week academic sprint:

  • Weeks 1-2 (Requirements Engineering): Defined disaster classifications (Flood, Collapse, Fire, Medical), identified AWS Free Tier quota boundaries, and formulated JSON schemas.
  • Weeks 3-4 (Architecture & Design): Designed serverless microservice flows, structured DynamoDB partition keys, formulated Leaflet GIS map layers, and conceptualized the WebRTC HUD reticle.
  • Weeks 5-7 (Cloud Development & Deployment): Implemented Python Lambda handler (lambda_function.py), deployed DynamoDB tables, configured API Gateway routes with CORS, created S3 storage policies, and deployed the frontend via AWS Amplify.
  • Week 8 (Integration & Stress Testing): Validated end-to-end payload latency, calibrated mobile touch reticle positioning, verified Esri defense GIS map tile loading, and benchmarked API concurrency.
  • Weeks 9-10 (Monitoring & Cost Auditing): Configured CloudWatch alarms, verified multi-AZ automated failover, performed cost audits verifying ₹0.00 billing, and compiled technical documentation.

5.2 Deployment Steps

Step 1: DynamoDB Table Provisioning: Created table DisasterIncidents in region ap-south-1 (Mumbai) with primary partition key incident_id (String) and on-demand capacity billing.
Step 2: Amazon S3 Evidence Bucket Setup: Created bucket disaster-drone-evidence-nirmaan with public read policy for drone imagery and CORS configuration permitting GET/PUT requests from Amplify web clients.
Step 3: AWS Lambda Function Deployment: Deployed lambda_function.py with Python 3.11 runtime, configured environment variables (DYNAMODB_TABLE, S3_BUCKET, AWS_REGION), and attached IAM execution policies.
Step 4: Amazon API Gateway Configuration: Created HTTP API with routes POST /incidents, GET /incidents, and PATCH /incidents with Lambda Proxy Integration and CORS wildcards.
Step 5: AWS Amplify Frontend Deployment: Packaged static frontend into amplify_deployment.zip and deployed to AWS Amplify Hosting, achieving instant global HTTPS access.

5.3 Security and Cost Considerations

Security & IAM: AWS IAM least-privilege role policies restrict Lambda execution strictly to necessary DynamoDB tables and S3 buckets. S3 evidence objects utilize Pre-Signed URLs with 24-hour expiration. Strict CORS configurations protect API Gateway from cross-origin hijacking.
Cost Optimization: The entire cloud stack operates 100% within AWS Free Tier allowances (1,000,000 Lambda requests, 25 GB DynamoDB storage, 5 GB S3 storage, 1,000 SNS emails). Result: ₹0.00 / month.

9. Challenges and Learnings

  • CORS Pre-Flight Blocking on API Gateway: Browsers rejected POST and PATCH requests due to missing Cross-Origin Resource Sharing (CORS) headers. Resolution: Configured API Gateway CORS settings with wildcards and programmed lambda_function.py to explicitly return Access-Control-Allow-Origin: * and allowed method headers.
  • Drone Camera Mobile Reticle Calibration: On touch devices, reticle dragging was jumpy and failed to dynamically calculate distress probabilities based on victim coordinates. Resolution: Implemented unified pointer event listeners with coordinate bounding-box math and a toggle between Automatic AI Detection and Manual Touch Reticle.
  • Map Tile Server API Key Dependencies: Commercial tile services introduced watermarks or required paid API tokens. Resolution: Migrated to Esri ArcGIS Defense & Emergency GIS tile services (server.arcgisonline.com), which are 100% free, require no API key, and provide defense-grade basemaps.
  • S3 Object Permissions & Pre-Signed URLs: High-resolution drone evidence photos could not be rendered in the dashboard when S3 block-public-access was active. Resolution: Implemented cryptographically generated Amazon S3 Pre-Signed URLs in Python Boto3, granting secure, time-bounded (24-hour) access to incident media without exposing bucket secrets.

Appendix A: AWS Lambda Core Handler Excerpt (Python 3.11)

# AWS Lambda Serverless Disaster Payload Handler
import json, boto3, uuid, time, math, os

dynamodb = boto3.resource('dynamodb', region_name=os.environ.get('AWS_REGION', 'ap-south-1'))
table = dynamodb.Table(os.environ.get('DYNAMODB_TABLE', 'DisasterIncidents'))

def lambda_handler(event, context):
    method = event.get('requestContext', {}).get('http', {}).get('method', 'GET')
    
    # POST: Ingest new drone incident telemetry
    if method == 'POST':
        body = json.loads(event.get('body', '{}'))
        inc_id = f"INC-{int(time.time())}-{uuid.uuid4().hex[:6].upper()}"
        item = {
            'incident_id': inc_id,
            'category': body.get('category', 'Flood / Trapped'),
            'severity': body.get('severity', 'CRITICAL'),
            'latitude': str(body.get('latitude', 18.5204)),
            'longitude': str(body.get('longitude', 73.8567)),
            'confidence_score': body.get('confidence_score', '96.8%'),
            'status': 'NEEDS_RESCUE',
            'timestamp': int(time.time())
        }
        table.put_item(Item=item)
        return {
            'statusCode': 201,
            'headers': {'Access-Control-Allow-Origin': '*', 'Content-Type': 'application/json'},
            'body': json.dumps(item)
        }
